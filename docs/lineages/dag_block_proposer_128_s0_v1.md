# dag_block_proposer_128_s0_v1 — broad block proposals from a strong start

**Status:** `CLOSED` (2026-09-23) — **BROAD BLOCK PROPOSALS NO-GO**. Registered 2026-09-23 before fresh workflows; the signed protocol and runner were frozen before their results.

**Outcome.** On sixteen fresh 128-operation workflows, exhaustive up-to-three-round scoring of the widened critical/lock/setup/block-swap pool improves a 250 ms strong start by only **0.44% median** (maximum 2.58%), far below the signed 8% headroom bar. The 512-evaluation hand proposer has median capture 0.0 of that small gap; the under-half hardness bar is numerically met but cannot fund training without material oracle headroom. All 49 actual-HeROsim replays and the independent 94,183-proposal audit pass. No GNN was trained. Per the signed stop, discontinue local/block move-pool variants and reassess the decision and research question before another training proposal.

**Question.** At 128 operations with precedence, locks, setup classes and mixed hosts, does a GNN have a worthwhile *proposal* problem: can broad coordinated block moves improve a strong starting schedule by at least 8% while an equally budgeted hand proposer captures under half the available gain? The parent [fixed-order block screen](dag_block_stepwise_s0_v1.md) already failed at 384 operations, so this is not a rerun of its 96-per-family pool or a model ranking test on a cheaply exhaustible list. It widens each of the four move families to 1,024 proposals and starts them from a 250 ms compiled hand plan, not the weaker initializer.

## 2026-09-23 — fresh CPU screen and live gate: NO-GO

The [result](../../simulation_data/gnn_environment_search_v1/dag_block_proposer_128_s0_v1/read.json) covers all sixteen fresh physical workflows, seeds 166000–166015. The first-round pool contains **2,101–2,253** candidates per workflow (median **2,193**), taking a median **871 ms** to score completely. Up to three exhaustive rounds exact-score **87,641** block proposals on the fresh set. The strong common start stays under 250 ms (maximum **242.48 ms**); the preselected hand proposer uses exactly 512 evaluations and stays under 250 ms (maximum **39.55 ms**). Its unused wall-clock allowance cannot repair the failed oracle-headroom bar under the equal exact-evaluation cap.

The bounded block oracle improves the strong start on 13/16 cases, but by only **0.4358% median**; its maximum individual improvement is **2.5769%** and no case reaches 8%. Mean summed job completion cost changes from **4,704.00** at the common start to **4,677.94** under the oracle; the hand proposer averages **4,698.44**. The bounded oracle beats the hand on 11/16 cases, the hand beats it on 2, and 3 tie. Median hand capture is **0.0** because most extra hand searches find no improvement; zero-oracle-gain cases conservatively count as capture 1. This is a finite-pool finding, not an optimality certificate or a proof that every possible coordinated action lacks value.

The required live gate completed **49 actual-HeROsim runs / 6,272 operations**: one opened calibration start and strong start, hand and oracle on every fresh workflow. The [independent audit](../../simulation_data/gnn_environment_search_v1/dag_block_proposer_128_s0_v1/AUDIT.json) passes all **18** unique workflow identities, **94,183** re-scored calibration and fresh proposal costs, source and native fingerprints, native/independent plan objectives and completion times, and every live task placement and completion. No GPU was allocated.

**Decision.** Stop this line of local/block move-pool variants. The 128-operation pool is too broad to exhaust inside the serving budget, but its *best* sampled block outcome adds less than half a percent at the median once the starting plan is strong. A GNN cannot create an 8% gain by selecting from this bounded pool. The remaining research question is about a different decision with a demonstrable value gap—such as online reservation under evolving state—not another width, order or scorer for this static move family. Any such successor needs its own physics/decision mechanism screen and matched hand control.

## 2026-09-23 — signed CPU screen before fresh workflows

The shape is **16 jobs × 8 operations = 128 operations on 12 hosts**. Opened calibration seeds 161200/161201 are used only for feasibility and hand-control selection. With 1,024 proposals per family, the deterministic critical-chain, lock-chain, setup-class and block-swap pool contains 2,162–2,188 feasible plans and takes about **0.87–0.89 s** to score exactly, beyond the 250 ms proposal budget; a timed fixed-order pass covers about 600. The full pool from the strong hand start gains 0% and 0.041% on those two opened cases, and up to three exact block-descent rounds add no further gain. The calibrated compiled post-start control, seeded 79, uses 512 exact evaluations in 37–39 ms and weakly beats the timed fixed-order block scan on the two opened cases. These observations are exploratory and excluded from qualification.

The signed fresh set is **166000–166015**, disjoint from prior DAG gates. Each workflow gets the same strong start: the existing fastest/affinity and rank initializer plus compiled mixed-decoder search charged to **250 ms**. If it returns a non-delay schedule, translate it to chronological reservation rank and assert the translation does not worsen cost before any block proposal. The bounded oracle exhaustively scores the deterministic widened block pool from this common start, accepts a strict improvement, and repeats for at most **three rounds**. It is a feasible finite reference, never a global optimum. The preselected hand proposer starts from the identical plan, uses at most **512 exact evaluations and 250 ms**, and gets the same operation, precedence, lock, setup and host information that a future GNN proposer would receive. Do not grant either path free exact scores from the oracle.

The training GO requires **median fresh oracle gain ≥8% over the common strong start** and **median hand capture <50%** of the start-to-oracle gain. Define capture as 1 when the bounded oracle has no gain, so zero-headroom cases cannot imply false search hardness. If both pass, test residual graph information after strong 1/2/4-hop hand controls before registering matched bipartite GNN and MP-OFF training. No GPU allocation occurs before all pretraining bars pass. If either fails, **stop iterating on local/block move-pool variants and reassess the research question** rather than merely widening this pool again.

Regardless of the offline decision, replay one opened calibration start and every fresh start, hand and oracle plan in actual HeROsim: **49 live runs / 6,272 operations**. Audit workflow identity, every plan cost and completion time against native and independent replay, all task placements and resource events, proposal pool counts, source hashes and matched budgets. A live gate verifies execution, not a GNN win.
